## 链接管理

之前的链接管理，每 Connect 一次会生成一条长连接(ws)，每条长连接(ws)都会生成一条记录到redis，并且会记录到一个链接列表当中。

而这些链接记录作用在于，调用方可以通过 GetUserState 获取目标用户已连接的链接ID（有链接则返回最早那条，没有则返回已关闭），再通过 SendMessage 下发到指定链接。

那么问题就来了，调用方并不知道这些链接有什么区别，拿不拿到链接ID有没什么区别呢？调用方推消息的时候，直接按照 GetUserState 的逻辑选择一条链接下发不就好了？

除了链接ID显的意义不明之外，最大的问题在于存储这些记录会导致redis的负载随时间推移线性增长，给存储造成很大的压力，所以有必要进行改造

改造后的方案如下：

### 接口逻辑
1. 连接建立

	每次 Connect 进来一条长连接，连接存储到本地缓存，然后将连接用户ID添加到redis指定topic下，节点地址添加到redis指定用户下。
	
	连接关闭时，清理本地缓存，将节点从redis用户下清除。需要检查节点列表是否为空，为空时清除topic下面用户。

2. 下发消息
	
	消息下发有3个接口，SendMessage（指定连接）、SendMessageByUser（指定用户）、SendMessageByTopic（指定topic）
	
	因为不按照连接维度存储，所以SendMessage会受到影响。为了兼容性可以保留现有接口，但不对连接ID进行识别。

	因为之前暴露连接ID对于调用方来说意义不大，所以取消暴露连接ID之后，这里也不再额外暴露信息

	发送消息时，先检查本地是否有连接，有则直接发送，无则删除用户下的本节点信息。然后选择一个节点进行转发。

3. 用户状态

	主要是建连、断连相关信息，可以直接从redis读取，多节点取其中一个即可（改单连接则只有单节点）。
	
	在目前多个节点的情况下，最好是能够将不同节点的信息集成到一个key下，否则遍历节点会比较麻烦。

	但聚合之后，何时删除是一个问题，按照之前的逻辑，是设置有效期让redis自动删除。

	目前的设想是，删除之前检查节点数，多个节点的情况下直接删除当前节点，只剩一个节点时设置整个key过期


### 存储结构

1. 本地缓存

	连接存储，目前是允许单用户多连接的，所以必须采用双重存储。如果后续改成单连接，可以改成单层结构

	```go
	map[string]map[string]Conn

	"appname:topic:userid" -> {"conn_id1"->Conn, "conn_id2"->Conn }
	```	

2. redis存储

	用户分组（set）,  记录用户在那个topic分组，用于群发消息（目前没用到，可以先预留）
	```sh
	"vlink:ws:user:appname:topic" -> ["user_id1", "user_id2"]
	```
	
	用户连接（zset）, 记录连接的节点
	```sh
	"vlink:ws:connect:appname:topic:userid" -> ["node1", "node2"]
	```
	
	用户状态（hash）, 存储节点连接状态信息。将多个节点集成到一个hash下
	```sh
	"vlink:ws:state:appname:topic:userid" -> {
		"node1:connect"->ts, "node1:disconnect"->ts
		"node2:connect"->ts, "node2:disconnect"->ts
	}
	```

### 生命周期

1. 生成连接，调用方通过 Connect 生成一条长连接(ws)，添加到本地缓存列表，当前节点node添加到redis用户连接列表，当前用户userid添加到redis指定topic下，更新节点连接状态

    - node 或 userid 添加失败时，上行消息正常，下行消息可能会找不到可用的节点而失败，

	- 所以最好使用 multi 命令同时添加两项，失败时直接关闭连接

    - 单一节点可以承载相同用户的多条连接，那么后续连接会重复触发存储，
	
	- 通过检查本地缓存的连接数，避免重复触发。并发连接可以通过本地的排他锁实现

	- 节点状态是由单一节点上的多条连接聚合而来的。应当在第一连接建立时更新连接时间（connect_time），在最后一条连接断开时更新断连（disconnect_time）。
	
	- 也可以记录连接数，但要想清楚对业务方的作用，目前监控层面已经通过智研上报实现了 
	

2. 读消息，循环读取长连接消息，心跳消息直接返回，其他消息通过回调推送

	- 要尽量保证上行消息的可达性，通过重试实现。


3. 写消息，接到下行消息之后，如当前节点无长连接，需要转发给有连接的节点。

	- 转发消息类似于函数递归，转发目标以节点单位，目标节点可能会发生继续转发的情况，没有明确的终止条件，可能出现无限递归的情况。

	- 节点转发消息时，应当通过metadata标记转发消息，禁止目标节点继续转发。


4. 关闭连接，清理本地缓存连接，清理redis存储

	- 本地连接为0时，清理redis存储的节点和用户信息。
	如果后续区分多端时，要在多端全部关闭之后再清除用户。

	- 遇到异常关闭（不能正常执行关闭逻辑），或者在执行关闭时异常推出，要保证redis存储能够被清理掉

	- redis 存储的信息会引导其他节点转发消息给异常节点，该节点检查到本地没有连接时，应当执行清除逻辑，并返回失败响应

	- 是否存在一种情况，当前节点异常退出之后，其他节点找不到该节点，比如重启后IP变化或缩容，导致存储无法清除？

	- 那么是否应该由请求节点拿到失败响应后，主动清理节点信息？但存在误伤的可能，比如节点之间暂时不通，但节点上的长连接是正常的
